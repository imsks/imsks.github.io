Why Civic AI Demands a Higher Standard
When Spotify recommends a song you don't like, the stakes are zero. When Rajniti generates an AI summary that incorrectly attributes a criminal case to an innocent politician, we have potentially influenced a democratic vote with false information. That is not a product bug. It is a civic harm. This framework defines how we prevent it, contain it, and correct it.

III Source Attribution Standards — Non-Negotiable Rules
Every fact has a source. Every source is visible. Every source is clickable.
100% Coverage · Gates Q2
What Gets Attributed
Every attendance figure — linked to Lok Sabha/Vidhan Sabha session records
Every asset value — linked to ECI affidavit PDF (page-level anchor)
Every criminal case disclosure — linked to affidavit and court record where available
Every AI summary — labelled with source data used, confidence level, and last-updated date
How Attribution is Displayed
Inline superscript citation on every data point — tap to view source
"AI Analysis" persistent badge on all synthesised summaries — visually distinct from verified facts
Last-updated timestamp visible on every profile — banner alert when data >30 days old
"Limited data available" label when ECI source coverage is below 80% completeness
What Is Never Allowed
Presenting AI-generated content without an explicit AI label
Publishing a data point without linking to its primary source
A/B testing source attribution — this is a product values commitment, not an optimization variable
Removing attribution to save screen space or improve visual cleanliness

Recency bias — latest session overweights
AI summaries trained on most recent session data will overweight short-term performance. A politician who attended every session in a 5-year tenure but missed the last session looks poor in a recency-weighted model.
Summaries explicitly state time range. Full tenure view available to premium users. Recency weighting disclosed in methodology.
Incumbency bias — more data for incumbents
Incumbent politicians have longer, richer ECI data histories than first-time candidates. AI summaries for first-time candidates are necessarily thinner — which may be misread as poor performance rather than limited data history.
"First-time candidate" label. Separate comparison criteria for incumbents vs first-time candidates. Explicit disclosure of data vintage.

The Ethical Line — What We Will Not Optimise
Source attribution is not an A/B test variable. It is a product values commitment. We will not run an experiment that shows some voters unattributed political data to measure whether attribution reduces conversion. Some decisions are made on principle. This is one of them. The same applies to AI labelling, the corrections log, and the 48-hour review SLA.
VII Three Transparency Obligations — What Users Are Owed
1
Know when they are reading AI vs. verified fact
AI-generated content and verified source data must be visually distinct at all times. Not a footnote. Not a settings page. A persistent, always-visible label in the primary content area. Users cannot make informed decisions about AI output if they cannot identify what is AI output.
Standard: Persistent "AI Analysis" badge. Cannot be hidden.
2
Know when their data was last updated
Every politician profile must display the data freshness clearly. When ECI data is more than 30 days old, a visible banner communicates this. A voter who makes a decision based on pre-election session data without knowing it is 6 months old has been misled — not intentionally, but consequentially.
Standard: Last-updated timestamp on every profile. Banner alert at 30 days.
3
Know that their corrections go somewhere real
A correction mechanism that accepts reports but never acts on them is not transparency — it is the appearance of transparency. Every user who submits a report receives a response within 48 hours. Every confirmed correction is published in the public corrections log. The log is linked in the product footer.
Standard: 48h response SLA. Public corrections log. No silent fixes for errors with civic impact.
VIII PM Responsibility When AI Gets It Wrong
The PM owns these four things — not "fixing it quickly"
Incident Classification
Hallucination (AI invented), data error (source was wrong), framing error (technically correct but misleading), or outdated data? Each has a different fix, different root cause, and different prevention strategy. Classifying correctly is the PM's first job.
Severity Assessment
How many users saw it? Was it shared? Is an election in the next 30 days? Severity determines response speed and resource allocation. A wrong AI summary with 3 views and no shares is different from one that was shared in a WhatsApp group of 500 voters two days before polling day.
Correction Protocol Decision
Silent fix, user notification, or public statement? In civic tech, a silent fix to an error that may have influenced voting behavior is ethically insufficient — even if it is operationally convenient. The PM makes this call, owns it, and documents it.
Prevention Investment
After every incident: what prompt constraint, confidence threshold, or data pipeline check would have prevented this? The post-incident review is not complete until it produces a specific, implementable change to the system. "We'll be more careful" is not a prevention strategy.
IX Closing Statement — The Trust Compact
What Rajniti Commits to Every Voter Who Uses This Product
Every fact we show you comes from a named, verified source — and you can check it yourself. Every AI summary is labelled as AI and cannot be mistaken for an official record. When we get something wrong, we will tell you, correct it publicly, and explain how we prevented it from happening again. This framework is not a compliance document. It is the proof that Rajniti is serious about the responsibility that comes with helping Indian citizens make better democratic decisions.
